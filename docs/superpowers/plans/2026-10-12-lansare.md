# Lansare și documentația de predare — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Site-ul se publică automat după CI verde: `main` pe producție, `staging` pe subdomeniul de test. Staging-ul nu se indexează. Apache primește configurarea potrivită (HTTPS, 404, antete de securitate, cache). Operatorul primește documentația de predare în română.

**Architecture:**
- **Modul de build:** `SITE_ENV` (`production` | `staging` | nesetat) e expus codului ca `import.meta.env.SITE_ENV` prin `vite.define` în `astro.config.ts`. Funcția pură `isIndexable(env)` decide `noindex` și `robots.txt`.
- **Apache:** `public/.htaccess` ajunge în `dist/`.
- **Publicarea:** un workflow nou, `deploy.yml`, pornește la `workflow_run` după `CI` reușit, pe `main` sau `staging`. Construiește cu `SITE_ENV` corespunzător și urcă prin SFTP cu `lftp`, folosind `scripts/deploy.sh`. Repornește aplicația Node prin `tmp/restart.txt`.
- **Comutatorul:** totul e oprit până la `vars.DEPLOY_ENABLED == 'true'`, setat când există hosting.

**Tech Stack:** Astro 7.3.8 static, GitHub Actions (`workflow_run`, environments `production`/`staging`), `lftp` (din apt pe `ubuntu-latest`), Apache `.htaccess` pe cPanel, Passenger pentru `/api`.

**Spec:** `docs/superpowers/specs/2026-10-09-site-englishminds-design.md` (§10 Publicare și operare, §12 dependențe de la client, §14 etapa 8)

## Global Constraints

- Fără `Co-Authored-By` sau mențiuni Claude în commituri și PR-uri.
- Nicio dependență npm nouă.
- `process.env` se citește doar în `astro.config.ts` (deja excepție ESLint) și în `server/config/environment.ts`.
- Niciun secret în repo: cheile SSH, host-urile, utilizatorii și căile vin din GitHub environment secrets/vars. Documentația numește variabilele, nu valorile.
- Publicarea nu șterge pe server ce nu e al site-ului static:
  - `api/`: aplicația Passenger și `.htaccess`-ul generat de cPanel pentru ea;
  - `.well-known/`: certificatele SSL;
  - `cgi-bin/`.
- Fără `SITE_ENV` (local, CI), site-ul rămâne indexabil, ca testele existente pe `dist/` să rămână valabile. Doar `SITE_ENV=staging` pune `noindex` și `Disallow: /`.
- Build-ul de producție eșuează cât timp `site.ts` are `TODO`. Deci publicarea pe producție e blocată automat până la completarea datelor, iar staging-ul merge fără ele.
- Documentația e în română, scrisă pentru un operator netehnic. Fiecare pas are locul exact (meniul din cPanel, fișierul din repo).
- `npm run verify` verde și E2E verde la final de task. Commituri Conventional, în engleză, la imperativ.

## Review Focus

1. **Staging indexat de Google:** cu `SITE_ENV=staging`, fiecare pagină are `noindex`, iar `robots.txt` are `Disallow: /` și nu are `Sitemap`. Test pe un build de staging (Task 1).
2. **`mirror --delete` care șterge aplicația `/api` sau certificatul.** Dry-run-ul scriptului arată excluderile, iar un test verifică excluderile în comanda generată (Task 2).
3. **Publicare pe producție din greșeală înainte de lansare:** jobul are condiția `vars.DEPLOY_ENABLED == 'true'` și rulează doar după `CI` reușit pe `main`/`staging` (Task 2).
4. **`.htaccess` care strică `/api` sau slash-ul final:** redirecționarea HTTPS și regulile nu rescriu `/api/*`. `ErrorDocument 404` trimite la `/404.html`. Test pe conținutul din `dist/` (Task 1).
5. **Documentație incompletă la predare:** fiecare dependență de la client din spec §12 apare în `docs/operare/lansare.md`, cu cine o furnizează și unde se pune (Task 3).

`src/shared/seo/site-env.ts`:

```ts
export type SiteEnv = 'production' | 'staging' | 'development';

export function siteEnv(raw: string | undefined): SiteEnv {
  return raw === 'production' || raw === 'staging' ? raw : 'development';
}

/** Staging must never be indexed; local and CI builds stay indexable so the dist checks describe production. */
export function isIndexable(env: SiteEnv): boolean {
  return env !== 'staging';
}
```

- [ ] **Step 1: Scriptul**

`scripts/deploy.sh`:

```bash
#!/usr/bin/env bash
# Uploads the built site (dist/) and the Node server (dist-server/) over SFTP, then restarts Passenger.
# Never deletes the Passenger app folder (api/), SSL challenges (.well-known/) or cgi-bin/ on the server.
set -euo pipefail

DRY_RUN=false
if [[ "${1:-}" == "--dry-run" ]]; then DRY_RUN=true; fi

: "${DEPLOY_HOST:?missing}" "${DEPLOY_USER:?missing}" "${DEPLOY_WEB_ROOT:?missing}" "${DEPLOY_APP_ROOT:?missing}"
DEPLOY_PORT="${DEPLOY_PORT:-22}"

for required in dist/index.html dist-server/app.cjs dist-server/purge-expired-leads.cjs; do
  [[ -f "$required" ]] || { echo "deploy: $required is missing, build first" >&2; exit 1; }
done

COMMANDS=$(cat <<EOF
set net:max-retries 2
set net:timeout 30
mirror --reverse --delete --verbose --exclude-glob api/ --exclude-glob .well-known/ --exclude-glob cgi-bin/ dist/ ${DEPLOY_WEB_ROOT}
mkdir -p -f ${DEPLOY_APP_ROOT}/tmp
put -O ${DEPLOY_APP_ROOT} dist-server/app.cjs
put -O ${DEPLOY_APP_ROOT} dist-server/purge-expired-leads.cjs
put -O ${DEPLOY_APP_ROOT}/tmp /dev/null -o restart.txt
bye
EOF
)

if $DRY_RUN; then
  echo "deploy (dry run) to sftp://${DEPLOY_USER}@${DEPLOY_HOST}:${DEPLOY_PORT}"
  echo "$COMMANDS"
  exit 0
fi

: "${DEPLOY_KEY_FILE:?missing}" "${DEPLOY_KNOWN_HOSTS_FILE:?missing}"
lftp -u "${DEPLOY_USER}," -p "${DEPLOY_PORT}" \
  -e "set sftp:connect-program 'ssh -a -x -i ${DEPLOY_KEY_FILE} -o UserKnownHostsFile=${DEPLOY_KNOWN_HOSTS_FILE} -o StrictHostKeyChecking=yes'; ${COMMANDS}" \
  "sftp://${DEPLOY_HOST}"
```

Comanda `put ... /dev/null -o restart.txt` creează sau suprascrie fișierul. Passenger repornește la schimbarea datei lui. Dacă `lftp` nu acceptă forma asta, folosește un fișier local gol `dist-server/restart.txt`, creat de script și urcat cu `put -O …/tmp`. Notează asta în raport.

`chmod +x` prin git: `git update-index --chmod=+x scripts/deploy.sh`.

- [ ] **Step 3: Workflow-ul**

`.github/workflows/deploy.yml`:

```yaml
name: Deploy

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main, staging]

concurrency:
  group: deploy-${{ github.event.workflow_run.head_branch }}
  cancel-in-progress: false

jobs:
  deploy:
    if: >-
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.event == 'push' &&
      vars.DEPLOY_ENABLED == 'true'
    runs-on: ubuntu-latest
    environment: ${{ github.event.workflow_run.head_branch == 'main' && 'production' || 'staging' }}
    env:
      SITE_ENV: ${{ github.event.workflow_run.head_branch == 'main' && 'production' || 'staging' }}
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm run build:server
      - run: sudo apt-get update && sudo apt-get install -y lftp
      - name: Write SSH credentials
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$DEPLOY_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          printf '%s\n' "$DEPLOY_KNOWN_HOSTS" > ~/.ssh/known_hosts
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          DEPLOY_KNOWN_HOSTS: ${{ secrets.DEPLOY_KNOWN_HOSTS }}
      - run: bash scripts/deploy.sh
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_PORT: ${{ vars.DEPLOY_PORT }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
          DEPLOY_WEB_ROOT: ${{ vars.DEPLOY_WEB_ROOT }}
          DEPLOY_APP_ROOT: ${{ vars.DEPLOY_APP_ROOT }}
          DEPLOY_KEY_FILE: /home/runner/.ssh/deploy_key
          DEPLOY_KNOWN_HOSTS_FILE: /home/runner/.ssh/known_hosts
```

`workflow_run` pe CI-ul cu ambele joburi (`verify` și `browser`) înseamnă că publicarea pornește doar dacă trec și testele în browser și Lighthouse. Notează asta într-un comentariu de o linie.

## Decizii

1. **`workflow_run` după `CI`, nu un job în `ci.yml`.** Publicarea rulează doar pe push în `main`/`staging`, după ce ambele joburi de test au trecut, cu secretele izolate în environment-uri.
2. **`DEPLOY_ENABLED` oprit implicit.** Hostingul nu există încă, deci workflow-ul nu face nimic până la configurare.
3. **`lftp mirror --delete` cu excluderi explicite.** Altfel `mirror` ar șterge aplicația Passenger (`api/`) și provocările SSL.
4. **Staging construit cu `SITE_ENV=staging`.** Permite `TODO` (build-ul de producție nu) și pune `noindex` + `Disallow: /`. Parola de staging se pune din cPanel (Directory Privacy), nu din repo, pentru că calea `AuthUserFile` depinde de server.
5. **HSTS fără `includeSubDomains`/`preload`.** Clientul poate avea alte subdomenii pe HTTP.
6. **Fără CSP în etapa asta.** Tagurile Google/Meta și scripturile inline Astro cer o politică atent calibrată. Se adaugă după lansare, cu `Content-Security-Policy-Report-Only` întâi. Trecut în `lansare.md` la „după lansare”.
